# UI

## Context and Design Philosophy

This component is a static browser client for the Business Analyst persona. It is the human-facing entry point to the pipeline: the visitor picks a bundled sample or uploads their own SNP data, and views the result — predicted ancestral population, confidence score, and top contributing markers.

The UI is a demo interface, not a production web app. It is plain HTML, CSS, and JavaScript with no server-side runtime and no build-time framework, published to GitHub Pages by a GitHub Actions workflow. It owns no ML logic: live predictions are `fetch` calls from the browser straight to the inference API (`docs/llds/06_deployment.md § API routes`).

The design is shaped by one constraint: a demo visitor should never stare at a spinner on their first click. The page itself is static and loads from a CDN. The bundled samples carry precomputed results, so selecting one renders immediately with no API call. Only an uploaded file reaches the live API, and the page warms the Lambda as soon as it loads so the cold start overlaps with the visitor choosing a file.

## User Flow

```
                 Page load ──► fire-and-forget GET /health (warm-up)
                     │
      ┌──────────────┴───────────────┐
      ▼                              ▼
1a. Select a bundled sample     1b. Upload own VCF → [Run Prediction]
      │                              │
      ▼                              ▼
  Fetch precomputed result      Validate in browser → POST /predict
  (static JSON, no API call)         │
      │                              │
      └──────────────┬───────────────┘
                     ▼
2. Results panel:
   - Source line ("Precomputed result for Sample SNP 2" / "Live prediction")
   - Predicted ancestral population label
   - Confidence score (percentage + progress bar)
   - Top-20 contributing markers (ranked table + horizontal bar chart of SHAP values)
```

The two paths are independent. Selecting a sample renders that sample's result at once; it does not need the Run Prediction button. Run Prediction submits the uploaded file only. The results panel always shows the outcome of the visitor's most recent action, whichever path it came from. **Latest action wins:** each sample selection or Run Prediction starts a new action and supersedes any earlier one still pending. Superseding takes effect at once: the loading indicator and the Run Prediction button switch to the new action's state, and the superseded action's in-flight `fetch` is cancelled through its `AbortController`. If a response for a superseded action still arrives, it is discarded and nothing is rendered. Selecting "None — use uploaded file" is not an action: it supersedes nothing, and a pending sample fetch or live prediction still renders when it completes.

## Site Structure

```
site/
  index.html
  app.js          ← page logic, as an ES module: state, requests, rendering, logging
  vcf.js          ← pure VCF checks used before upload (extension, size, single-sample header); no DOM
  styles.css
  config.js       ← generated at deploy time; defines the API endpoint
  samples/        ← assembled at deploy time from the repo's samples/ directory
    manifest.json
    sample_snp_1.vcf
    sample_snp_1.result.json
    ...
```

`config.js` and `site/samples/` are build outputs, not committed. The repo-root `samples/` directory stays the single source of truth for sample files, shared with the Python tests.

`bin/assemble_site.py` builds a servable site directory from these pieces: it copies `site/`, writes `config.js` from an endpoint value, and writes `samples/manifest.json` with the matching sample and result files, failing if a sample has no result. The CI deploy job, `bin/05_ui.sh`, and the browser tests all assemble the site through it, so the published site, the local preview, and the tested site are built the same way. It uses only the Python standard library.

## Sample Files and Precomputed Results

Three bundled sample VCF files live in `samples/` at the repo root, matching the glob `sample_snp_[0-9]*.vcf`. Each represents a population-representative chr15 SNP profile targeting a distinct ancestral group (African/Yoruba, East Asian/Han Chinese, European/Utah). Other `.vcf` files in `samples/` (such as `sample_snp_upload.vcf`, used to demo the upload path) are not listed as samples.

Each sample has a committed precomputed result beside it: `sample_snp_N.result.json`, holding the exact `PredictionResult` JSON body the live `POST /predict` returned for that file. Because it is byte-for-byte the API's response shape, one renderer serves both paths. Its `model_artifact_version` field records which model produced it.

**Generating precomputed results.** `bin/06_precompute_samples.sh` posts each sample VCF to the deployed `POST /predict` endpoint, read from `PHENO_API_ENDPOINT` (the value `bin/04_deploy.sh` prints), and writes each response body unchanged to `samples/sample_snp_N.result.json`. The write is all-or-nothing: responses are collected first, and the result files are replaced only if every sample returned `200`, so a failure partway through never leaves results from two different models side by side. The operator runs it after each `sam deploy` that binds a new `MODEL_RUN_ID`, and commits the output. The precomputed results are therefore real outputs of the deployed model, not fixtures.

Because every result records the `model_artifact_version` that produced it, the committed set is checked for consistency: all result files must carry the same `model_artifact_version`. A mixed set means the samples were precomputed against different deployments, and the demo would present results from two models as if they were one.

**Manifest.** A static site cannot list a directory, so the site deploy job writes `site/samples/manifest.json`: an array of `{"label": "Sample SNP N", "vcf": "sample_snp_N.vcf", "result": "sample_snp_N.result.json"}` entries, one per file matching `sample_snp_[0-9]*.vcf`, ordered by N. The label is derived from the numeric suffix. If any matching VCF has no `.result.json` beside it, the deploy job fails and nothing is published: a missing result is caught at deploy time, and the client fallback above covers only runtime fetch failures.

**Client behavior.**
- On page load the client fetches `samples/manifest.json`. If the fetch fails or the manifest is empty, the "Try a sample" section is hidden silently.
- Selecting a sample fetches its `result` JSON and renders it with the source line "Precomputed result for Sample SNP N". No API call is made.
- If a sample's result JSON cannot be fetched or does not parse, the client falls back to a live prediction: it fetches the sample's VCF and posts it to `POST /predict`, exactly as for an upload, and labels the result "Live prediction".
- Sample files skip browser-side validation (extension, size, sample-count checks) — they are pre-validated bundled fixtures.
- Selecting "None — use uploaded file" clears nothing; it only deselects the sample.
- If the fallback is needed but the API endpoint is not configured, the client shows "The prediction service is not configured." and sends nothing, as for Run Prediction.

## Warm-up

On page load, the client sends one `GET {endpoint}/health` request and does not wait on it. The response, status, and any network error are ignored: no UI change, no retry, nothing shown to the visitor. Its only purpose is to start the Lambda's cold start (container start plus model load, per `docs/llds/06_deployment.md § API routes`) while the visitor is still choosing a file, so the first live `POST /predict` lands on a warm container.

The warm-up is sent once per page load. There is no scheduled keep-warm ping (see `docs/high-level-design.md § Key Design Decisions`). If the endpoint is not configured, the warm-up is skipped.

## API Endpoint Configuration

The site deploy job writes `site/config.js` from the GitHub repository variable `PHENO_API_ENDPOINT` (the API Gateway base URL, which is public and not a secret). `config.js` sets a single global, `window.PHENO_API_ENDPOINT`.

If the endpoint is empty or `config.js` is absent, the sample path still works (it needs no API). Run Prediction then shows "The prediction service is not configured." and logs an error; no request is sent.

## Live Prediction Request

Run Prediction is disabled while no file is chosen in the upload control, whatever the sample selection.

Run Prediction reads the uploaded file as UTF-8 text and sends:

```
POST {endpoint}/predict
Content-Type: application/json

{"vcf": "<file contents>"}
```

This is the request contract in `DEPLOY-BE-027`. The `Content-Type: application/json` header makes this a CORS non-simple request, so the browser sends an `OPTIONS` preflight first; the API's CORS configuration answers it (`docs/llds/06_deployment.md § CORS`).

While the request is in flight, the client shows a loading indicator and disables Run Prediction. The request is aborted after 35 seconds. The Lambda times out at 29 seconds and the gateway at 30 (`docs/llds/06_deployment.md § Lambda Execution`), so a server-side answer normally arrives first; the client timeout covers a stalled network. On any outcome the button is re-enabled.

## Input Validation

The client validates an uploaded file before sending it:
- File name must end in `.vcf`, compared case-insensitively (`sample.VCF` is accepted)
- File size limit: 4 MiB (4,194,304 bytes; browser-side guard, not a security boundary). The file travels JSON-encoded, and every tab — the VCF column separator — becomes the two-byte escape `\t`, so the request body can be much larger than the file. Lambda rejects synchronous request payloads over 6 MB; a 4 MiB file stays under that limit after encoding, where a 5 MB one may not.
- The file must contain exactly one sample: it must have a `#CHROM` header line, and that line must have exactly one column after `FORMAT`. Multi-sample VCFs, sites-only VCFs, and files with no `#CHROM` line are rejected.

Validation errors are shown inline next to the upload control and nothing is sent. Sample files skip these checks.

## Error Handling

The Lambda returns structured error bodies `{"error": <code>, "detail": <message>}` (see `docs/llds/06_deployment.md § Error contract`). The client maps known codes to messages, shown inline in the results area:

| Response | User-facing message |
|---|---|
| `MODEL_UNAVAILABLE` | "The prediction service is starting up or unavailable — please try again in a moment." |
| `INVALID_VCF` | "The uploaded VCF could not be processed (multi-sample file, malformed format, or no usable variants)." |
| `INVALID_INPUT` | "The request was rejected as malformed — please reload and try again." |
| `INFERENCE_FAILED`, `INTERNAL_ERROR` | "The prediction service encountered an error — please try again or contact support." |
| HTTP 503 or 504 whose body is not in the `{"error", "detail"}` format (API Gateway's own response, e.g. an integration timeout) | "The prediction service is starting up or unavailable — please try again in a moment." (same as `MODEL_UNAVAILABLE`) |
| HTTP 429 (API throttling, `docs/llds/06_deployment.md § Throttling`) | "The demo is busy right now — please try again in a few seconds." |

API Gateway's throttled `429` responses carry the configured `Access-Control-Allow-Origin` header (verified against the deployed API: every `429` in two bursts of 40 and 60 concurrent requests from the Pages origin carried it), so the browser can read the status and the 429 message is what a throttled visitor sees. A network error therefore means the API was genuinely unreachable, and keeps the generic message.
| Unknown or missing code, network error, timeout | Generic message: "The prediction request failed — please try again." |

The client does not retry on its own; the visitor re-submits after seeing the message. An error message shown in the results area replaces whatever result was showing there, so a stale result from an earlier action is never displayed beside an error about a later one.

## Results Display

The results panel shows, for a `PredictionResult` from either path:
- A source line: "Precomputed result for Sample SNP N" or "Live prediction".
- The predicted ancestral population label.
- The confidence score as a percentage rounded to the nearest whole number (0.825 shows as 83%), with a progress bar.
- A ranked table of the top contributing markers (`PRED-DATA-002`): rank, variant ID, chromosome, position, and SHAP contribution value.
- A horizontal bar chart of the same markers, drawn as inline SVG: one bar per marker, sorted by absolute SHAP value descending (largest at the top), each bar labelled with its variant ID. Bars extend from a shared zero axis — positive contributions to the right, negative to the left — so bar length shows magnitude and direction shows sign. Lengths are scaled to the largest absolute value in that chart, whose bar fills its half of the chart width.

## Observability

The browser has no stdout for a log aggregator, so client-side logging is for a developer with the browser's developer console open. All client log output goes through a single `log(level, event, fields)` helper in `app.js`, which writes one JSON object per event (`{"level", "event", ...fields}`) via `console.info` / `console.warn` / `console.error`. The server side of every request is logged by the Lambda per `DEPLOY-BE-022`, so production triage of API failures does not depend on client logs.

| Event | Level | Key fields |
|---|---|---|
| API endpoint not configured | ERROR | — |
| Upload fails browser-side validation | WARN | `filename`, `errors` |
| Sample selected, precomputed result shown | INFO | `sample`, `phenotype`, `confidence` |
| Precomputed result unavailable, falling back to live | WARN | `sample`, `error` |
| Live prediction request sent | INFO | `input` (`upload` or `sample`), `filename`, `size_bytes` |
| Live prediction result displayed | INFO | `phenotype`, `confidence`, `markers` |
| API returned an HTTP error | ERROR | `status`, `error_code`, `detail` |
| Network error, timeout, or unexpected exception | ERROR | `error`, `stack` |

The warm-up request logs nothing; its outcome is deliberately ignored.

## Execution and Delivery

**Production.** The site is published by a `deploy` job in the existing CI workflow, `.github/workflows/ci.yaml`. The job declares `needs: test`, so it runs only after lint and tests pass, and only for pushes to `main` and manual dispatches on `main` — never for pull requests. It assembles the site (copies `site/` and the matching sample files with their result JSON, writes `samples/manifest.json` and `config.js`), uploads it with `actions/upload-pages-artifact`, and publishes with `actions/deploy-pages`. The site is served at `https://mattjtravers.github.io/genomic-ancestry-pipeline/`. The README's "Open Demo" button links there.

The job assembles the site with `python3 bin/assemble_site.py` (standard library only, so it needs no dependency install), passing the repository variable `PHENO_API_ENDPOINT` as the endpoint; a sample without a result file fails the assembly and therefore the job, so nothing is published. It runs in the `github-pages` environment with the permissions Pages deployment requires (`pages: write`, `id-token: write`, `contents: read`), and a `pages` concurrency group lets an in-progress deployment finish rather than be cancelled by a newer push.

Two one-time repository settings are prerequisites, outside the code: GitHub Pages' build source set to **GitHub Actions**, and the repository variable `PHENO_API_ENDPOINT` set to the API's base URL. If the variable is unset, the job still publishes, and the page runs samples-only and reports itself unconfigured.

All paths in the client are relative (`samples/manifest.json`, `config.js`), so the site works under the `/genomic-ancestry-pipeline/` sub-path and from a local server alike.

**Local.** `bash bin/05_ui.sh` assembles the same site with `bin/assemble_site.py` into a temporary directory, using `PHENO_API_ENDPOINT` from the environment for `config.js`, serves it with `python -m http.server 8000`, and removes the directory when the server stops. With `PHENO_API_ENDPOINT` unset it warns and serves a samples-only preview. Port 8000 is fixed: `http://localhost:8000` is the only local origin the API's CORS configuration allows (`docs/llds/06_deployment.md § CORS`).

## Testing Approach

Client behavior is tested in a real browser with **pytest-playwright**, so the tests run under the project's existing `uv run pytest`; the CI test job installs the browser with `uv run playwright install --with-deps chromium` before running them. A fixture assembles the site with `bin/assemble_site.py` and serves it locally, with the endpoint pointed at a path on the same local origin; API calls are intercepted with Playwright's `page.route`, so tests never touch AWS and do not depend on CORS behaviour, which is verified against the deployed API instead (`docs/llds/06_deployment.md § CORS`). Timing-dependent behaviour — a request still in flight when the visitor acts again, the 35-second client timeout — is driven with a test-only `fetch` wrapper and Playwright's clock rather than real delays. This lets tests assert directly on what the visitor sees (rendered labels, error text, disabled buttons) and on which requests were or were not sent (for example, that selecting a sample sends no `POST /predict`).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| UI framework | Plain HTML/CSS/JS ES module, no build step | React/Vue with a bundler, Streamlit, Gradio | The UI is one form and one results panel; a framework and bundler add a Node toolchain to a Python project for no user-visible gain. Streamlit and Gradio need a running Python server, which rules out static hosting. |
| UI delivery | GitHub Pages, published by a `deploy` job in `ci.yaml` with `needs: test` | Streamlit Community Cloud, S3 + CloudFront, Netlify; a separate Pages workflow | Pages is free, CDN-served, and lives in the same repo and CI system. A job inside the CI workflow can depend on the test job directly, so a red build never publishes; a separate workflow would need a cross-workflow trigger to get the same guarantee. S3 + CloudFront works but adds AWS resources and cost for no gain; Netlify adds a third-party account. See `docs/high-level-design.md § Key Design Decisions`. |
| Prediction integration | Browser `fetch` directly to the HTTP API | A proxy backend | A proxy would reintroduce a server to host and wake. The API is public either way; CORS restricts which pages can call it from a browser, and throttling caps cost (`docs/llds/06_deployment.md`). |
| Sample results | Precomputed `PredictionResult` JSON committed beside each sample, generated from the deployed API | Call the live API for samples; generate results in the Pages workflow at deploy time; hand-written fixtures | Precomputed results make the most common demo click instant and immune to cold starts. Generating them from the deployed API keeps them real model outputs; generating in the Pages workflow would make every site deploy depend on the Lambda being up. |
| Missing precomputed result | Fail the deploy job when a sample has no result file; at runtime, fall back to a live prediction if the result cannot be fetched | Publish anyway and rely on the fallback; show an error at runtime | A missing file is a deploy mistake and is cheapest to catch before publishing. A runtime fetch failure is not the visitor's fault, and the live API can still answer, at the cost of a possible cold start. |
| Superseded live request | Cancel it with `AbortController` and switch the UI to the new action at once | Let it finish and ignore the result; queue actions | The visitor's latest click is what they want to see; a spinner for an abandoned request would contradict the panel. Cancelling also frees the browser connection. |
| Sample selection trigger | Selecting a sample renders its result immediately | Select, then press Run Prediction | With a precomputed result there is nothing to wait for; an extra click adds nothing. |
| Warm-up | One fire-and-forget `GET /health` per page load | Scheduled keep-warm ping; provisioned concurrency; no warm-up | Costs one request per visit and only when someone is actually looking. Always-on options pay around the clock for a mostly idle demo. |
| API endpoint config | `config.js` written by the Pages workflow from the repo variable `PHENO_API_ENDPOINT` | Hard-code the URL in `app.js`; commit a config file | Keeps the endpoint out of source, so a redeployed stack needs only a variable change. The project's existing variable name is kept. |
| Client module split | `app.js` (page logic) plus `vcf.js` (pure VCF checks) | One `app.js` for everything | The upload checks are pure functions of a file's name, size, and text; keeping them free of DOM and network code makes them readable on their own and lets the page logic stay about state and rendering. |
| Site assembly | One script, `bin/assemble_site.py`, used by the deploy job, `bin/05_ui.sh`, and the tests | Inline shell steps in the workflow; separate logic per caller | Three callers assembling the site three ways would let the published site drift from what was tested. A standard-library Python script runs unchanged in CI, locally, and under pytest. |
| Chart rendering | Inline SVG drawn by `app.js` | Chart.js or Plotly from a CDN | Twenty bars do not justify a charting library; inline SVG has no external dependency to load or pin. |
| Client logging | JSON objects to the browser console through one helper | Send client logs to a collection endpoint; no client logging | There is no aggregator for browser output, and adding a log-ingest endpoint would add surface and cost. Server-side failures are already logged by the Lambda. |
| Browser test harness | pytest-playwright with `page.route` API stubs | Jest/Vitest unit tests on JS; manual testing only | Stays inside the existing `uv` + `pytest` toolchain; tests exercise the real page as a visitor sees it. |
| File input format | VCF only | VCF + CSV | VCF is the sole data format end-to-end. |
| Phenotype field in request | Not sent | User-selected phenotype in the POST body | The model determines ancestral population from the VCF alone; there is no target-phenotype concept. |
| JSON download button | None | Offer the raw result for download | The demo targets non-technical stakeholders; the results panel stays focused on the visual summary. |

## Open Questions & Future Decisions

### Deferred
1. Detecting stale precomputed results — the site could compare each result's `model_artifact_version` with the deployed model and warn when they differ. Today regeneration is an operator step after `sam deploy`.
2. Authentication for the UI — none in the demo; CORS is not authentication.
